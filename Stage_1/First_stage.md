# Этап 1. Сбор и анализ требований — решение кейса «Бронирование номеров в отеле»

## 1. Описание предметной области
Отель предоставляет услуги по временному проживанию гостей в номерах различных категорий (Стандарт, Люкс). Номера имеют свои уникальные номера и фиксированную стоимость за сутки. Клиенты (гости) могут осуществлять бронирование номеров на определенные даты, а также заказывать дополнительные услуги (завтрак, трансфер, спа), которые увеличивают общую стоимость брони. 

Процесс обслуживают сотрудники отеля (администраторы), которые оформляют заезд/выезд гостей, принимают оплату и управляют справочниками (номера, услуги). Система должна контролировать доступность номеров на выбранные даты, рассчитывать итоговую стоимость проживания с учетом услуг и не допускать двойного бронирования одного номера на одни и те же даты.

### Ключевые процессы
Каждый процесс — это цепочка действий, которая имеет бизнес-смысл и меняет данные в системе.

| Процесс | Шаги | Что меняется в данных |
| :--- | :--- | :--- |
| **Регистрация гостя** | Гость предоставляет данные &rarr; администратор вносит его в базу | Создается запись в «Клиент» |
| **Поиск свободного номера** | Гость или администратор ищет номера по категориям и датам | Чтение каталога; данные не меняются |
| **Оформление бронирования** | Клиент выбирает номер и даты &rarr; администратор фиксирует бронь | Создается запись в «Бронирование», статус номера меняется на «Забронирован» |
| **Добавление услуги** | К существующей брони выбирается доп. услуга | Создается запись в промежуточной таблице «Услуги в брони» |
| **Оформление заезда (Заселение)** | Гость приезжает &rarr; администратор подтверждает заезд | Статус брони меняется на «Активна», статус номера &rarr; «Занят» |
| **Оформление выезда (Расчет)** | Гость выезжает &rarr; рассчитывается финальная стоимость &rarr; фиксируется оплата | Статус брони &rarr; «Завершена», статус номера &rarr; «Свободен» |
| **Управление номерами** | Администратор добавляет новый номер или меняет стоимость | Создаются/обновляются записи в «Номер» |

### Ограничения
Ограничения — это правила, которые нельзя нарушать.

| Тип | Ограничение | Источник |
| :--- | :--- | :--- |
| **Структурное** | У каждого бронирования должен быть конкретный клиент и номер | Логика процесса |
| **Бизнес-правило** | Один номер не может быть забронирован на пересекающиеся даты | Физическая реальность |
| **Бизнес-правило** | Дата выезда должна быть строго позже даты заезда | Логика процесса |
| **Техническое** | Номер комнаты должен быть уникальным | Техническое |
| **Техническое** | Телефон клиента должен быть уникальным | Техническое |

## 2. Роли пользователей
В системе выделены две основные роли: **Клиент** и **Администратор**.

### Роль «Клиент»
Клиент — это гость отеля, который регистрируется, ищет свободные номера на даты, создает бронирования и просматривает историю своих заказов.

| Действие | Входные данные | Результат | Ограничения |
| :--- | :--- | :--- | :--- |
| **Регистрация** | ФИО, телефон, паспорт | Создан профиль клиента | Телефон уникален |
| **Поиск номеров** | Даты заезда/выезда, категория | Список свободных номеров | Только чтение |
| **Создание брони** | ID номера, даты заезда/выезда | Создана бронь (статус «Новая») | Номер свободен на эти даты |
| **Просмотр своих броней**| ID клиента | Список личных бронирований | Видит только свои данные |

### Роль «Администратор»
Администратор — сотрудник отеля, который управляет фондом номеров, подтверждает заезды и выезды, добавляет услуги и фиксирует оплату.

| Действие | Входные данные | Результат | Ограничения |
| :--- | :--- | :--- | :--- |
| **Подтверждение заезда**| ID брони | Статус брони &rarr; «Активна» | Текущая дата совпадает с датой заезда |
| **Оформление выезда** | ID брони | Расчет стоимости, статус &rarr; «Завершена» | Бронь была активна |
| **Добавление услуги к брони** | ID брони, ID услуги, количество | Услуга привязана к брони | Бронь не завершена |
| **Управление номерами** | Номер комнаты, категория, цена | Новый номер в базе данных | Номер комнаты уникален |

## 3. Бизнес-правила
Бизнес-правило — это утверждение о том, что должно быть истинно в данных всегда.

| № | Бизнес-правило | Категория | Где реализуется |
| :--- | :--- | :--- | :--- |
| **Б1** | Один номер не может быть забронирован двумя клиентами на одни даты одновременно | Ограничение состояния | Логика приложения (проверка на пересечение интервалов) |
| **Б2** | Дата выезда должна быть строго больше даты заезда | Ограничение по времени | `CHECK (дата_выезда > дата_заезда)` |
| **Б3** | Цена номера за сутки не может быть отрицательной | Ограничение значения | `CHECK (цена_сутки >= 0)` |
| **Б4** | Стоимость дополнительной услуги не может быть отрицательной | Ограничение значения | `CHECK (цена_услуги >= 0)` |
| **Б5** | Номер комнаты должен быть уникальным | Ограничение уникальности | `UNIQUE (номер_комнаты)` |
| **Б6** | Номер телефона клиента должен быть уникальным | Ограничение уникальности | `UNIQUE (телефон)` |

## 4. Состав данных и объемы
Ниже представлено описание структуры таблиц (сущностей), их атрибутов на абстрактном уровне и прогноз объемов данных через 1 год и 5 лет.

### Описание таблиц

* **Таблица «Клиент»:** данные для идентификации гостя.
  * *Атрибуты:* ID клиента, Фамилия, Имя, Телефон, Паспорт.
* **Таблица «Номер»:** информация о жилом фонде отеля.
  * *Атрибуты:* ID номера, Номер комнаты, Категория (Стандарт/Люкс), Цена за сутки.
* **Таблица «Услуга»:** справочник доступных дополнительных услуг.
  * *Атрибуты:* ID услуги, Название услуги, Цена услуги.
* **Таблица «Бронирование»:** информация о заказах номеров.
  * *Атрибуты:* ID брони, Ссылка на клиента, Ссылка на номер, Дата заезда, Дата выезда, Статус брони (Новая/Активна/Завершена).
* **Таблица «Услуги в брони»:** связь M:N для фиксации заказанных услуг.
  * *Атрибуты:* Ссылка на бронь, Ссылка на услугу, Количество.

### Оценка объемов данных
Масштаб: небольшой отель на ~50 номеров.

| Наименование таблицы | Оценка на 1 год | Оценка на 5 лет | Комментарий |
| :--- | :--- | :--- | :--- |
| **Номер** | 50 | 50 | Фонд отеля стабилен |
| **Услуга** | 10 | 15 | Справочник доп. услуг растет медленно |
| **Клиент** | 1 500 | 5 000 | Поток новых и постоянных клиентов |
| **Бронирование** | 3 000 | 15 000 | В среднем ~8-10 бронирований в день |
| **Услуги в брони** | 4 500 | 22 500 | ~1.5 услуги на одно бронирование |

## 5. Частота операций
Частота операций определяет приоритеты оптимизации БД (где нужны индексы для чтения, а где важна быстрая запись).

| Процесс | Тип операции | Частота | Важность |
| :--- | :--- | :--- | :--- |
| Поиск свободных номеров по датам | Чтение (OLTP) | 150/день | **Высокая** (клиент ждет на сайте) |
| Создание новой брони | Запись (OLTP) | 10/день | **Высокая** (критично для бизнеса) |
| Оформление заезда/выезда | Обновление (OLTP) | 20/день | **Высокая** (очередь на стойке регистрации) |
| Добавление доп. услуг | Запись (OLTP) | 15/день | Средняя |
| Отчет по загрузке отеля за месяц | Чтение (OLAP) | 1/месяц | Низкая (можно выполнять в фоне) |

---

## 6. Требования к производительности
Ожидаемое время ответа системы на ключевые запросы:

* **П1:** Поиск свободных номеров на выбранные даты — **не более 200 мс** при 50 одновременных запросах (самая частая операция на сайте).
* **П2:** Проверка доступности конкретного номера (проверка на отсутствие пересечений дат перед записью) — **не более 50 мс** (критично для бизнес-правила Б1).
* **П3:** Формирование ежемесячного аналитического отчета по доходам и загрузке — **не более 3 секунд**.
